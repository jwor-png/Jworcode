This skill follows `cuan/skills/SHARED_STANDARDS.md` and the common
structure in `cuan/skills/_TEMPLATE.md`. Read `SHARED_STANDARDS.md`
before producing any output under this skill.

## 1. Purpose and trigger
Turns a working session's content into a clean, structured update to
Cuan's operational files, so nothing discussed is lost between
sessions and no other session has to re-derive context that already
exists. Trigger at the end of a substantial thread, or when John
explicitly asks for something to be "handed over," "logged," or
"folded into" Cuan's files.

## 2. Required inputs
- The session content to be handed over.
- Which file(s) it actually belongs in (board.md, ventures_dossier.md,
  a venture-specific file, etc.) — if unclear, ask rather than guess a
  destination.
- Explicit confirmation before moving anything that originated as
  personal reflection, Council material, or a ChatGPT draft into an
  operational file — this is not assumed by default (see Shared
  Standards boundary rule).

## 3. Workflow
1. Separate what actually happened (confirmed facts, decisions made,
   actions completed with evidence) from what was merely discussed,
   proposed, or intended.
2. Attach explicit dates to every development — not "recently" or
   "this week," but the actual date it happened or was discussed.
3. Identify every person and venture named, using the correct
   documented name/spelling from existing Cuan files, flagging any
   name that could not be confirmed rather than silently guessing.
4. Write the handover in Cuan's existing voice and structure for that
   file (match the surrounding content's tone and format, don't impose
   a different style).
5. **Boundary check, mandatory before writing anything:** if any of the
   material originated in a ChatGPT or Council context, confirm this
   was explicitly meant to move into Cuan's operational record. Do not
   assume a Council reflection or a ChatGPT-authored document should
   become part of the shared operational file just because it was
   shared in this session — that requires John's explicit instruction,
   not an inference from context.
6. Present what will be written and where, before committing it, if
   the update is significant enough that John would want to see it
   first.

## 4. Output format
A clear before/after: what is being added, to which file(s), and a
short note of anything left open or unconfirmed. If written directly
into a file, the actual diff/addition should be visible to John, not
buried.

## 5. Quality checks
- No item is logged as a completed action unless there is direct
  evidence it was completed.
- Every date is explicit, not relative.
- No Council or ChatGPT-originated material has been moved into an
  operational file without explicit instruction to do so.
- Uncertainty (a mis-heard name, an unconfirmed fact, an open question)
  is preserved visibly in the handover, not smoothed away for a
  tidier-looking update.
- Names and venture references match what's already documented
  elsewhere in Cuan's files, with any discrepancy flagged rather than
  silently resolved in one direction.

## 6. Handling of missing information
If it's unclear which file something belongs in, whether a plan was
actually acted on, or whether Council/ChatGPT material is meant to
cross into Cuan's operational record, stop and ask. This skill's
entire value depends on the record being trustworthy — a fast but
wrong handover is worse than no handover.

## 7. Completion criteria
The handover is complete when a future session reading only Cuan's
files (with no memory of this conversation) would have an accurate,
appropriately-dated, appropriately-uncertain picture of what happened
and what's still open, with no operational file containing anything
that crossed the ChatGPT/Council boundary without explicit permission.
